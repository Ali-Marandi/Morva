# Technical Assessment — M4.79 Revalidation

## Position
M4.79 is the persistence edge following the verified M4.78 mainline. This clean-mainline candidate transfers only the M4.79 persistence/API/migration/tests/docs and preserves the newer web changes already present on `main`.

## Root cause from the previous candidate
The prior M4.79 CI run failed in `test_m4_79_post_persists_verification_receipt`. A SQLite connection created in the test thread was reused by FastAPI's TestClient worker thread, raising `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`. The failure was reproducible in both the focused M4.79 workflow and the full pytest workflow.

## Corrective change
- The M4.79 test fixture now uses a shared in-memory SQLite engine configured with `check_same_thread=False` and `StaticPool`.
- The HTTP request uses a fresh SQLAlchemy Session from a sessionmaker instead of reusing the fixture Session across threads.
- Source fixtures are committed before the HTTP request so the request Session reads a stable persisted state.
- The M4.78 test helper accepts an explicit source hash, allowing deterministic independent source-history cases.

## Validation status
**IN PROGRESS.** The original candidate's M4.79 workflow and full test suite failed on the cross-thread SQLite issue. The corrective patch is committed to a clean branch based on the latest verified mainline; the focused M4.79 workflow, migrations, full suite, lint, dependency audit and web checks must succeed on the new branch before this milestone is considered validated.

## Safety boundary
Verification/readiness metadata only. No provider execution, credentials, payment mutation, legal-rate inference or production authorization is introduced. Production payroll/payment remains blocked by the six canonical production-readiness gates.
